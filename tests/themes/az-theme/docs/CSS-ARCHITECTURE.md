# CSS Architecture

## Naming convention

All new frontend theme classes use the `az-` prefix. Components use a stable name such as `.az-product-card` or `.az-button`. Complex components use BEM-style elements: `.az-product-card__image`, `.az-product-card__content`, `.az-product-card__title` and `.az-product-card__price`. State classes use `az-is-*` when a state must be represented in markup.

## Root wrapper

`header.php` opens the shared root wrapper and `footer.php` closes it:

```html
<div id="page" class="az-site">
```

`body_class()` remains in place for WordPress, plugin compatibility, third-party integrations and debugging. It is not the primary AZ CSS scope.

## Component class

Components should be styleable without knowing which page renders them:

```css
.az-product-card {}
.az-product-card__image {}
.az-product-card__title {}
.az-button {}
```

Avoid selectors that describe the entire DOM path. The component class belongs on the element that owns the behavior and appearance.

## Mandatory reuse rule

Before adding a CSS rule, search the parent theme and child theme for an existing component that owns the same visual responsibility. Shared appearance must be defined once in the component selector. Page, template and plugin compatibility selectors may only control placement or integration details that cannot live in the component.

Do not repeat the component's `padding`, `border`, `border-radius`, `background`, `color`, typography or transition in a page-specific selector. Add a modifier class instead:

```html
<a class="az-button az-button--secondary az-button--small" href="#">Action</a>
```

```css
.az-button { /* shared structure and default appearance */ }
.az-button--secondary { /* color only */ }
.az-button--small { /* size only */ }
:where(.az-cart-page) .az-button { /* placement only when necessary */ }
```

Required workflow for every CSS change:

1. Search all parent and child stylesheets for the component and property being changed.
2. Update the owning component rule instead of adding a later override.
3. Use an `az-` modifier for a genuine visual variant.
4. Keep page rules limited to layout properties such as `width`, `margin`, `grid-*`, `flex-*` or positioning.
5. Remove obsolete compatibility rules after their markup has adopted the component class.

### Shared button API

All frontend action buttons use `.az-button`. The compatibility selectors for buttons generated by WooCommerce are maintained beside this component in `style.css` and must not be duplicated in `css/woocommerce.css`.

- `.az-button`: shared structure and Primary color.
- `.az-button--secondary`: Secondary color.
- `.az-button--accent`: Accent color.
- `.az-button--danger`: Error/danger color.
- `.az-button--outline`: transparent outlined style.
- `.az-button--small`: compact padding and font size.
- `.az-button--block`: full container width.

Never create color names such as `.btn-red`; use semantic AZ modifiers so Theme Advanced colors remain the single source of truth.

## Page class

Page-specific behavior belongs on a content wrapper or `main` element:

```html
<main class="az-main az-shop-page">
```

Current page scopes include `.az-landing-page`, `.az-blog-page`, `.az-single-post`, `.az-shop-page`, `.az-product-page` and `.az-cart-page`.

Prefer low-specificity page rules:

```css
:where(.az-shop-page) .az-product-card {}
```

## CSS variables

Theme variables belong at `:root` and use the `--az-*` prefix:

```css
:root {
  --az-primary: #f7941d;
  --az-text: #424242;
  --az-container: 1110px;
}
```

Do not define theme variables under `body.az-storefront`, `body.az-theme` or another body class.

## Specificity rules

Keep selectors shallow. Prefer one component class, then a single page scope only when necessary. Avoid body selectors, long descendant chains, element-qualified component selectors and `!important`. Use `!important` only to resolve a documented third-party conflict that cannot be solved by ownership or load order.

## Legacy migration

Legacy selectors are audited first. The migration sequence is:

1. Add an AZ selector and AZ class alongside the legacy class.
2. Update the relevant template/markup.
3. Test the affected desktop, mobile, WooCommerce active and WooCommerce inactive states.
4. Remove the legacy selector only after no supported template or integration relies on it.

The current compatibility layer intentionally retains `body.az-storefront ...`, `.az-*` and legacy inline rules in selected files. They are not patterns for new code.

## Forbidden patterns

- `body.az-storefront .xxx`
- `body.az-theme .xxx`
- `body.woocommerce ...` or `body.single-product ...` as the theme architecture scope
- Deep selector nesting such as `.az-site .az-main .woocommerce ul.products li.product .title`
- New project classes or variables without the `az-` / `--az-` prefix
- Unnecessary `!important`
